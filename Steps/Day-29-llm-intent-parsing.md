# Day 29 — LLM Intent Parsing (Ollama, proposal only)

**Status:** IMPLEMENTED — awaiting review (not committed)

## Objective

Connect the first real LLM provider to OpenBIM Studio: a local model served by Ollama converts a controlled natural-language wall-editing request into a **validated `EditProperty` command proposal**.

Day 29 is not an execution milestone. No command is executed, the model is not changed, and no geometry is regenerated.

## Model

| | |
|---|---|
| Runtime | Ollama 0.40.1 (local, Windows), HTTP API `http://127.0.0.1:11434` |
| Default model | `llama3.2:3b` (3.2B, Q4_K_M) |
| Also installed | `gemma3:4b` (4.3B, Q4_K_M) — selectable with `OLLAMA_MODEL=gemma3:4b`; not evaluated on Day 29 |
| Generation | `stream: false`, `temperature: 0`, `num_ctx: 8192`, JSON-schema `format` |

Nothing was downloaded or installed; no Python package was added (`httpx` was already in the venv; it is now listed explicitly in `requirements.txt`).

## Architecture

The generative model interprets intent; deterministic application logic validates (and, from a later milestone, executes) the command.

```text
Natural language (POST /api/ai/prompt)
  → ContextBuilder (spatial tree + selected entity)
  → LLMClient, provider "ollama" (POST /api/chat, schema-constrained)
  → OutputParser (JSON → AIResponse / Command)
  → validate_command()  — Day-27 contract, for every command
  → validated EditProperty proposal (millimetres) or reported rejection
  → STOP
```

Two layers of control, deliberately distinct:

- **Syntactic:** Ollama's `format` JSON schema (`EDIT_PROPERTY_RESPONSE_SCHEMA`) restricts the reply to `{intent, commands, text}` with at most one `EditProperty` command, `pset` = `Qto_WallBaseQuantities`, `property` ∈ Length/Height/Thickness, `unit` ∈ mm/m. A test keeps the schema enums equal to the contract's `EDITABLE_PROPERTIES` / `UNIT_TO_MM`.
- **Semantic (authoritative):** `AIChatService` runs the existing Day-27 `validate_command()` on every parsed command. Validation is not duplicated in the provider.

## Explicit boundary

Day 29 does not execute commands.

- The AI path never calls `execute_command()`, `EntityStore.set_prop()`, ParametricGeometry, GeometryFactory, WallGenerator, OpenSCADEngine or OpenSCAD.
- Accepted commands are returned as canonical proposals (`value` in mm, `unit: "mm"`), which re-validate to the same edit. The response text is generated by the server ("Proposed (not applied): set Qto_WallBaseQuantities.Height of 'wall-001' to 3200 mm."), so model text claiming a change was made is not shown when commands are returned.
- Rejected commands are dropped from `commands` and reported in `text` with the contract's reason (e.g. `Rejected CreateComponent: unsupported_command (...)`).
- **CreateComponent cannot escape.** Only validated `EditProperty` commands are ever returned, so the frontend's legacy `AIChatPanel` `CreateComponent → POST /api/scad/render` branch has nothing to act on. The frontend currently ignores `EditProperty`, so proposals are shown as text only. `/api/scad/render` itself is unchanged (Day 30 safety boundary).
- The Day-28 transaction mechanism is unchanged.

## Implementation

- **`core/config.py`** — `OLLAMA_BASE_URL` (default `http://127.0.0.1:11434`), `OLLAMA_MODEL` (default `llama3.2:3b`), `OLLAMA_TIMEOUT_SECONDS` (default 120; the first call includes model load), `ollama_num_ctx = 8192` (explicit, to avoid Ollama's smaller default silently truncating the context). Default `LLM_PROVIDER` remains `anthropic`.
- **`main.py`** — passes the Ollama settings to `LLMClient`; API key only for `anthropic`/`openai` (none for `ollama`); passes the `EntityStore` to `AIChatService` for read-only validation.
- **`services/llm/llm_client.py`** — `provider == "ollama"` branch: Day-29 task prompt (`EDIT_PROPERTY_SYSTEM_PROMPT`; the older broad `SYSTEM_PROMPT` is kept for the other providers) and response schema. Connection failure, timeout, non-200, non-JSON body, missing/empty content, and a prompt that fills `num_ctx` (`prompt_eval_count ≥ num_ctx`) all raise `LLMClientError`. The Anthropic/OpenAI branches are unchanged (still unimplemented).
- **`services/llm/chat_service.py`** — validates every command, returns proposals/rejections as above; a stale `selected_guid` (`EntityNotFoundError`) now gives a graceful reply without calling the LLM, instead of a 500. The contract is imported as a module (`from services.commands import contract`) because `contract.py` imports `services.llm.models`; the cycle is import-order safe (checked both ways).
- **`.env.example`** — documents the Ollama variables and that nothing loads `backend/.env` (variables must be set in the environment that starts the backend). No `.env` loading was added; environment variables are sufficient.

## Tests

`backend/tests/test_llm_intent_parsing.py` (17 tests). Ollama is replaced by `httpx.MockTransport`; the real LLMClient, OutputParser, ContextBuilder, contract and EntityStore (temporary model) are used. Needs neither Ollama nor OpenSCAD.

- Request shape: `POST /api/chat`, model, `stream: false`, `temperature: 0`, `num_ctx: 8192`, schema `format`, no auth header; valid reply parses and is accepted by the contract.
- Provider failures → `LLMClientError`: connection refused, timeout, HTTP 500, HTTP 404 (model missing), non-JSON body, non-object body, no message, empty content, context filled; missing configuration.
- Settings defaults (`anthropic` still default; `llama3.2:3b`; `OLLAMA_MODEL=gemma3:4b` selectable).
- Schema enums match the Day-27 contract.
- Service: valid command → canonical mm proposal, server-generated text, model unchanged; provider failures and invalid/mis-shaped JSON → graceful reply; no-command reply → "No change was proposed."; stale selection → graceful, LLM not called.
- Rejections (12 cases): CreateComponent, UpdateSelection, missing `target_guid`, extra parameter, unsupported property, unit `ft`, string value, 0, negative, 500 m, nonexistent GUID, door target — each absent from `commands`, reason reported; mixed reply returns only the valid command.
- Proposal-only invariant: spies on `executor.execute_command`, the `services.commands` re-export, `EntityStore.set_prop` and `OpenSCADEngine.render` are never called; an AST check forbids the `services/llm` modules from importing the executor, OpenSCAD, geometry or API layers or referencing `execute_command`/`set_prop`/`render`.
- Route: `POST /api/ai/prompt` with a CreateComponent reply → 200, `commands: []`, render never called; EditProperty reply → only canonical proposal, `set_prop` never called; stale selection → 200, not 500.

A mutation check (server-side validation bypassed in a scratch script) made the rejection/route/proposal tests fail (17 subtest failures), confirming they detect a bypass.

Full backend suite: **47 tests OK** (30 existing + 17 new), none skipped. `backend/data/model.json` SHA-256 `23de08c2…be345f` unchanged before and after.

## Live smoke test (integration check, not an evaluation)

Real `llama3.2:3b` through the real `AIChatService`, on a scratchpad copy of the model, selected wall `wall-001`. Spies confirmed `execute_command`, `set_prop` and `render` were called 0 times; the copy was unchanged. Timings are **preliminary integration timing**, not research performance results (single run, warm model except the first call; prompt ≈ 690 tokens of 8192).

| # | Request | Model output (params) | Result | Time |
|---|---|---|---|---|
| 1 | Make the selected wall 3.2 m high. | Height, **3200.0, "m"** | Rejected: `value_out_of_range` (3 200 000 mm) | 8.2 s (incl. model load) |
| 2 | Make the wall 4 metres long. | Length, 4, "m" | **Proposed** Length = 4000 mm | 1.8 s |
| 3 | Make the wall 250 mm thick. | Thickness, 250, "mm" | **Proposed** Thickness = 250 mm | 1.8 s |
| 4 | Make the wall 500 metres long. | Length, 500, "m" | Rejected: `value_out_of_range` (500 000 mm) | 1.8 s |
| 5 | Delete the wall. | no command | No change proposed | 0.9 s |
| 6 | Create a door in the wall. | no command | No change proposed | 0.8 s |
| 7 | Make the wall longer. | no command | No change proposed | 0.9 s |

With the final prompt, a re-run reproduced all seven outcomes (temperature 0).

### Observation: unit/value inconsistency (UNRESOLVED)

In #1 the model converted 3.2 m to 3200 but kept `unit: "m"`. The contract rejected it only because 3200 m exceeds the 100 m bound — a false rejection of a legitimate request. The same failure on a small value (e.g. "0.05 m thick" → `50, "m"` = 50 m) would **pass validation as a wrong proposal**. The preliminary pre-Day-29 audit test (a minimal hand-written context) did not show this; the real context lists the wall's quantities as bare millimetre numbers, which is a plausible cause (HYPOTHESIS).

One prompt revision was tried (explicit "no conversion" examples, and a note that context quantities are in mm). It did **not** fix #1 (`3200, "m"`) and **regressed** #7: "Make the wall longer." produced an invented `Length 1112 mm`, which the contract accepts. The revision was reverted; the table above is from the original Day-29 prompt. Further prompt tuning against this small set was not pursued, to avoid overfitting an informal test.

The contract validates *well-formedness and bounds*, not *faithfulness to the user's words*. Because Day 29 is proposal-only and the proposal is shown in explicit millimetres, no wrong value can be applied today, but this must be resolved before the AI → property bridge (Day 31).

RECOMMENDATION (needs approval): a small deterministic **grounding check** in `AIChatService` before proposing — accept a command only if its `value` appears as a number in the user's text and its `unit` agrees with the unit written next to it; otherwise report it as not grounded. This would reject both #1-style conversions and #7-style invented values without relying on the prompt. It is not implemented.

*These notes were added after Day 29 was implemented. They are not part of the original Day-29 change set, and everything above them is left as originally recorded.*

- **Status.** Day 29 was later accepted on review. As of this note, it is still uncommitted and will be checkpointed together with Day 30.
- **Day 30 added deterministic validation after `validate_command()`.** All three checks are in `backend/services/commands/provenance.py` and are called by `AIChatService` (see `Steps/Day-30-safety-boundary.md`):
  - numeric/unit provenance: `verify_provenance()`;
  - property consistency: `verify_property()`;
  - selected-target consistency: `verify_target()`, applied only when the request refers to the selection ("selected", "selection", "this wall").
- **The grounding-check recommendation above was superseded.** It was not implemented as written ("value appears as a number in the user's text"). The implemented check works differently:
  1. It extracts the request's single explicit quantity (digits plus an `mm`/`m` unit).
  2. The application converts that quantity to canonical millimetres (`Decimal`).
  3. It requires the proposal's millimetre value to equal it exactly. The proposal's value is converted by the contract from the LLM's value and unit.

  So "3.2 m" may be proposed as `3.2 m` or `3200 mm`, but not as `3200 m`. This is not a textual substring match. Requests with no explicit quantity, more than one quantity, or relative wording are rejected.
- **`/api/scad/render` and the frontend `AIChatPanel` `CreateComponent` branch are still present and unchanged.** The note above that says "(Day 30 safety boundary)" anticipated Day 30 changing them, but Day 30 did not modify either. What Day 29–30 ensure is that the AI proposal path (`POST /api/ai/prompt`) never returns a `CreateComponent` (or any unsupported) command to that branch. Hardening the endpoint itself remains a separate, later task.
- **"Unchanged: `services/commands/`" referred to the Day-29 change set alone.** Day 30 then changed that package: it added `provenance.py`, added rejection reasons to `contract.py` and exports to `__init__.py`. Day 30 also changed one fixture prompt in `backend/tests/test_llm_intent_parsing.py` (see Day-30 §8).
